# Практическая работа №4 «Горизонтально масштабируемый сервис»

Сервис построен по микросервисной архитектуре:
управляющий контейнер создаёт задания, брокер передаёт их, а реплицируемые
контейнеры-работники выполняют вычисления.

## Состав сервиса

| Сервис | Тип контейнера | Назначение |
|---|---|---|
| `producer` | управляющий | раз в секунду отправляет число в очередь |
| `broker` | RabbitMQ | хранит и распределяет задания |
| `worker` | работник | получает число и вычисляет его квадрат |

`producer` и `worker` собираются из разных Dockerfile. Все реплики `worker`
создаются из одного образа.

## Запуск с одним работником

```sh
docker compose up --build --scale worker=1
```

## Проверка горизонтального масштабирования

Запуск трёх работников:

```sh
docker compose up --build --scale worker=3
```

Запуск десяти работников:

```sh
docker compose up --build --scale worker=10
```

В логах будут разные идентификаторы работников:

```text
producer-1  | Producer: sent task 7, number=7
worker-1    | Worker ...: task 7, 7^2=49
worker-2    | Worker ...: task 8, 8^2=64
worker-3    | Worker ...: task 9, 9^2=81
```

Это показывает, что один поток заданий распределяется между несколькими
однотипными контейнерами.

## Остановка

Нажать `Ctrl+C`, затем выполнить:

```sh
docker compose down
```

## Как работает балансировка

Все работники слушают одну очередь RabbitMQ `tasks`. Брокер выдаёт каждое
сообщение только одному свободному работнику. Параметр `prefetch_count=1`
не позволяет одному контейнеру заранее забрать много заданий, поэтому нагрузка
распределяется между репликами.

## Соответствие условию

| Требование | Реализация |
|---|---|
| Не менее двух типов контейнеров | `producer` и `worker` |
| Один брокер | RabbitMQ |
| Управляющий контейнер | `producer` создаёт задания |
| Реплицируемые работники | сервис `worker` запускается с `--scale` |
| Балансировка между репликами | общая очередь RabbitMQ и `prefetch_count=1` |
| Произвольная функциональность | вычисление квадрата полученного числа |
